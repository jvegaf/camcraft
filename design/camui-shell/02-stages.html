Campilot — where the workflow went

This board used to argue a five-stage workflow carried by a strip across the top of the shell: Design → Edit → Toolpaths → Simulate → G-code. The delivered shell has no strip (S2 — the stage bar was removed and the workflow moved into the rail and into the open task). So the argument inverts. The workflow did not leave with the strip: it is carried by the rail, which offers the whole command table at once, and by whatever task the right panel has open, which is a thing being done rather than a place being stood. Nothing below argues a stage bar back into existence.

Every colour, size and radius here is a token in design/system.md: app bar 40 px, rail 200 px, a 22 px ruler on each of the canvas' top and left edges, inspector 288 px, status bar 26 px, brand block 62 px, control 24, row 26, radii 4 / 6 / 10, one hairline, icons 24 × 24 at 1.6 stroke, type 11 / 12 / 13 / 15 / 20 / 28.

01 The diagnosis same job, same data, two shells

Partitioning a window is not a workflow.

The frame can answer where a thing lives. It cannot answer what the operator is doing — which is exactly the question the strip was invented to answer. Removing the strip therefore only worked because the answer moved somewhere honest, and the three places below are where.

02 Where the workflow went the strip was never in the reference

It came from a guess, and a guess is not evidence

The strip was drawn from eight frames photographed off two video recordings: small, letterboxed, half the chrome cropped, so the shell's layout had to be inferred from what survived the crop. The fifteen full-resolution frames in design/prancheta-reference/ show no such strip in any state — not on an empty sheet, not mid-draw, not with a simulation playing. Not one of the fifteen draws it. The five stages were ours; S2 removed them, and with them the Stage enum, the readiness gates and the stage-scoped rail that had been built to serve them.

What the frames do show is the workflow, carried in three places that are already on screen.

a · The rail is not stage-scoped

One command table, five labelled groups, all of it reachable at once. The operator folds a group instead of remembering a mode: folding hides the chips and leaves the heading, so the rail always says what it holds, and a drawing command is one press from an edit command because nothing decided they belong to different moments.

b · The right panel carries the task

A task is open or closed, never a stage. Opening a ribbon category puts the task over the panel's body; ✕ closes it and the panel falls back to the selection's numbers. The two glyphs differ in exactly one fact — whether the draft survives the closing — because two glyphs that did the same thing would be a control that lies.

The header names what is being done, not which shelf the operator is standing at: a tab names a place, a task names an action.

c · What a command can do is decided by the document

There is no mode to be in, so nothing is hidden because of where the operator stands. Readiness is a fact about the document — what is selected, whether the drawing has a file, whether the strategy has a tool — never a property of a stage, and the shell says it in the two places a control can afford to explain itself: a control that has to say why is replaced by the sentence that says it (the panel's footer), and a row that must keep its shape is drawn dark with its reason attached (a menu row).

The rail is the third case: it never greys a chip. Every rail chip is pressable, because what a command can do is settled when it runs and reported in the status bar — so the operator never has to ask which mode is hiding a command. A stage could only ever say not yet; refused: says what was missing, on the frame it was missing in.

No rail command carries a single-key letter

The reference draws a letter beside every glyph because it binds every glyph. This shell answers F1, F2, Esc, Cmd+Z, Shift+Cmd+Z, Delete — and Backspace, which does the same — and F, and nothing else.

A letter printed under a chip that no key runs is the same lie as a count nobody measured, so the rail carries none. When the binding exists, the letter is drawn; until then the chip is a press, and the Shortcuts window is the list of what the keyboard really does.

One command, drawn greyed, with its reason

The rail's own twenty-eight chips are never drawn disabled: every one is pressable, and what a command can do is settled when it runs and reported in the status bar. The dead-control case lives where the operand is already known — a row whose one missing fact is the whole reason it will not run.

Trim stays dark until two vectors are selected, because a trim needs a target and a cutter. The sentence is never further away than the chip: it is the row's own teaching, and the row does not run when it is dark.

The same rule, twice more in the delivered shell: the material dialog's Continue stays dark while a dimension is zero, with the sentence under the plan that names the number; the tool library's Use this tool stays dark until a tree row is chosen.

04 The teaching voice four sentences that carry state without a strip

The strip's one honest job was to say what was missing. Four sentences do it now, quoted verbatim from the shell.

The panel's note about the document

Asked of the document, never of a mode. The DOCUMENT section of the job's task ends with the one fact the document is missing, and says nothing when it is missing nothing — a section that certified a gate it cannot check would be the strip again, in a sentence.

0 vectors on the sheet“Nothing drawn yet — 0 vectors on the sheet. Draw or import the shape you want to cut.”

0 toolpaths in the document“Nothing to cut yet — 0 toolpaths in the document. A toolpath comes from cam-cli toolpath and lands here finished.”

The status bar's hint, and a refusal

The right end of the bar carries the hint for the tool in hand, and the sentence the last action produced. A refusal is the same sentence prefixed refused: — never a colour, never a modal.

the hint for the tool in hand“Line — drag on the sheet to place it; Esc cancels”

pressing Save on a drawing with no file“refused: this drawing has no file yet — use Save As to name one, and Save writes to it from then on”

A control which cannot act is replaced by the sentence that says why — never drawn dead

In the strategy editor the footer holds one primary action, and while the draft is incomplete the button is not drawn at all. Its place is taken by the sentence:

where “Generate toolpath” would stand No tool yet — a strategy has to cut with something, so choose one from the tool library first.

The rule is the strip's real replacement. A stage told the operator to wait; a sentence tells them what is missing and where to get it. Where the row must keep its shape — a menu row, a chip whose reason is the only thing it has to say — the same reason rides on the dim chip instead, and that is the difference between a control that lies and one that explains.

What it refuses

  • A stage bar. The workflow is not a place, and a strip that claims to be one has to lie about the frame underneath it.
  • Tabs in the inspector. A tab names a shelf; a task names what is being done, and only the second one tells the operator why the panel changed.
  • A palette per stage. A command that moves when the mode changes is a command to hunt for. One table, five headings, one place to look.
  • A second accent. There is Sel and there is Cut; a third means the screen is telling two stories at once.
  • A dead control. A press that answers nothing is worse than a sentence that says what is missing.
  • A count nobody measured. A number in chrome is a claim, and a claim the shell cannot check is decoration with a number's authority.
